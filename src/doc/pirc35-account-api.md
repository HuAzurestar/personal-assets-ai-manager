# PIRC-35 account metadata

The versioned `/paam/ledger/v1/account-party`, `/account`, `/account-ref` resources manage person → management set → concrete own-source identity. POST creates metadata; GET `/{id}` reads it; PUT `/{id}/metadata` requires the displayed `expected_updated_time`. GET `/list` uses the existing JSON filter/sorter URL parameters and the exact four-key list body, default 20 / maximum 100.

Read projections add a derived `display_label` to person/set/ref, `party_name` to a set, and `account_name`, `party_id`, `party_name` to a ref. These are current ownership labels, not new columns, persisted identities or writable aliases. Ungrouped refs explicitly have `party_id=0` and empty ownership names. Ref labels use the public provider name, user name, masked reference/source identity and ownership; stable IDs and status remain visible as disambiguators. The same masked projection is used in Flow detail.

Each resource has `GET /search` with bounded candidate scanning, standard `page_size` (20, maximum 100), literal JSON `query`, optional `filter`, `sorter`, and condition-bound `cursor`. Search returns `items,total=null,page_size,next_cursor,has_more,scanned_count,elapsed_ms`; an empty hit batch may still have a continuation. Query capabilities are `name,display_label` for persons; additionally `party_name` for sets; additionally `institution,reference,source_namespace,source_identity,account_name,party_name` for refs. Matching occurs **after masking**, so a hidden account prefix cannot affect hits. A label term searches across its visible parts; multiple query expressions remain AND, never wildcard/SQL LIKE. Lists retain their exact four-key body and reject unsupported text parameters. Each read has a 30-second budget and pages/search responses a two-MiB limit. Ownership names are joined in a bounded query; per-page source timestamps are batched, not loaded once per row.

The related Position source-leg picker uses `GET /paam/financial/v1/position/{id}/leg/search` with literal `basis` terms and the same scan body. It is strictly scoped to that Position and its cursor cannot transfer to another object. Hits retain complete public leg data, Review state and bounded second-stage allocations; choosing a source still requires an original IN leg of a currently confirmed Review, with publication revalidation. Its existing list/sort semantics remain available.

Frontend text search in the common picker and Fact/Flow/Review lists automatically continues serial GET batches, including empty batches, after the first response is mounted. It shows cumulative scanned/hit counts, never a fabricated total, and offers pause/cancel. A phase allows up to 25 continuation batches or eight seconds between requests; a single in-flight read retains its server-side read budget and can be aborted. A phase limit is explicitly paused, not complete. The displayed result window pauses at 200 hits or two MiB of serialized items (one complete bounded response may cross the threshold; no response is sliced). Continuing a full window is labelled as replacing the current results, and only a successful next read replaces it. Cumulative progress and the cursor survive window changes; selection remains caller-owned. Failed reads preserve the last accepted cursor/results for user-directed retry. Changed conditions, route departure and dialog closure invalidate/abort old reads. No automatic write replay or cumulative candidate cutoff is introduced. Explicit list paging is unchanged.

Names are labels, not identities. Manual refs never silently merge by name, institution or account suffix. Only parser-certified complete bank own-account numbers in `abc:statement-v1`, `ccb:statement-v1`, `cmb:statement-v1` may create/reuse RELIABLE refs automatically. Payment methods, order numbers, counterparties, masked accounts and unknown identities cannot. The public metadata read always masks `reference` and `source_identity`; there is no unmasked metadata endpoint. Source namespace/identity/strength are immutable.

`Ledger.account_ref_id=0` means unknown/unbound identity. A known ref with `account_id=0` means identified but ungrouped. Initial ref/default creation and new Fact/source acceptance share the importer transaction. Reused Facts are not rebound or restored by evidence intake.

Changing a ref's `account_id` requires POST `/{id}/move-preview`, then `/{id}/move-command` with `preview_digest` and the original expected time. Preview discloses old/new person/set and affected Ledger count; lock-time recomputation protects against intervening ownership or Ledger changes. Cross-person movement is explicit. No metadata operation updates Fact or Ledger contents. A group remains attached to its original person; moving a concrete card uses the ref operation.

Status ACTIVE/CLOSED is maintenance metadata, not a money deletion filter. Existing cash of closed cards remains counted. Statement/snapshot intervals are 0 (manual) by default; this resource does not create new jobs or balance snapshots. Latest accepted source intake time is read-only and derived from actual source rows.

Account scopes resolve ref IDs through indexed SQL subqueries within the same read snapshot, avoiding thousands of literal IN parameters. They are filters, not sort keys. Position quantities and PIRC-36 balance snapshots remain separate from these metadata records.

All writes serialize before their controlling reads. Stale edits/move impacts report ENTITY_CHANGED; broken positive ownership chains report ACCOUNT_RELATION_BROKEN. Uncertain commits report RESULT_UNKNOWN: query current metadata/list and do not automatically repeat a create or move.
