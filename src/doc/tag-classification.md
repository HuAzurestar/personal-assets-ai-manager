# 综合消费分类

配置源：`src/asset/tag/classification.json`。这是静态、可编辑的业务配置，
不是关键词自动打标器；正式结果仍由模型生成 JSON，经校验后成为待审申请。

| 维度 | 候选标签 |
| --- | --- |
| 消费用途 | 医疗、出行、餐饮、服装、日用消耗品、食品生鲜、数码家电、居住缴费、教育学习、休闲娱乐、住宿旅游、通信订阅 |
| 购买渠道 | 网购、线下；不明确时维持未分类 |

例如网购药品可以产生“医疗”和“网购”两条独立申请；到店购买洗衣液可以
产生“日用消耗品”和“线下”。同一维度只建议一个标签，两维度分别调用模型，
费用及进度也分别计算。只看到淘宝/京东而没有商品用途时，只能确定渠道，
不能凭平台猜医疗或服装。微信、支付宝、现金不直接代表购买渠道。

用途规则默认 BAND，渠道规则 NONE；两条规则都按每分钟 CRON、共享 FIFO
串行工作，页大小和运行预算保持原合同。没有立即执行或独立重扫功能。
高额聚餐仍可归餐饮，小额纸巾仍是消耗品，金额不能单独决定分类。
转账、退款、报销、还款或混合用途不清时保留依据不足，不强行分类。

仅保留经审定的通用词和少量公开平台名称；身份、账号、联系方式、订单号、
具体病情等未知片段仍省略。模型准确率要另行用真实调用验证，离线协议测试
不能证明某个模型必然给出期望标签。审查通过前不改变正式标签、金额或账务。

服务级开关 `PAAM_AUTOTAG_REAL_ANALYSIS=1` 决定是否允许真实数据扫描，
不能与纯虚构验收开关同时启用。先确认外发授权、模型费用和凭据，再重启服务。
无须重新导入；已有规则从保存的游标继续，新规则从历史页开始。

给已有库安装新分类时，新建上述两个 View，而不扩展旧验收 View：
添加候选标签会使该 View 的旧规则版本/游标失效；使用独立 View 可以保留
原验收规则的游标、统计和待审申请。安装配置不等于同意启动收费扫描。

本地配置工具默认只读预检；明确加 `--apply` 才写入，新增规则始终停用。
工具复用完全匹配的配置，发现冲突停止，不覆盖用户修改，也不会停用旧规则。

```text
python src/script/configure_tag_classification.py --base-url http://127.0.0.1:18775 --model-id 2
python src/script/configure_tag_classification.py --base-url http://127.0.0.1:18775 --model-id 2 --apply
```
