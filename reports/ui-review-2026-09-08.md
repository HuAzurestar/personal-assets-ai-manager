# UI 需求核对与实际体验（2026-09-08）

结论：主要账务流程可以运行，但当前界面尚未形成完整的日常操作闭环。问题集中在标签维护入口缺失、导入结果反馈不完整、已排除流水的可追溯性、候选筛选错误和移动端操作负担。建议先解决这些问题，再调整视觉样式。

## 依据与验证范围

- 需求依据：README 的“当前 MVP（以本节为准）”“五页工作台”“当前标签状态（JSON）”“候选复核操作与汇总影响”和“SQLite 数据库观察”。仓库没有找到独立的需求分析文档。
- 程序：独立虚拟环境 `.venv`，FastAPI 服务 `http://127.0.0.1:8766`，仅绑定本机。体验数据库在 `data/ui-review-verified/`，使用构造的 68 条流水，不涉及用户真实账单。
- 实际操作：通过 Playwright 驱动本机 Edge，点击全部五个导航入口，体验空状态、导入、筛选、翻页、标签选择、创建视图、候选详情、处理与撤销、数据库查看；检查 390、700、740、1024、1440 像素宽度。
- UI 上传覆盖：支付宝 CSV、微信 CSV、微信 XLS/XLSX 多文件、微信密码 ZIP；错误模板、错误密码、确认时未重新输入密码、重复文件。
- 现有测试：`python -m pytest -q`，27 passed，2 项依赖弃用警告。
- 不宣称覆盖每个按钮与数据组合：未验证真实远程 LLM、每个平台与格式的完整交叉组合、所有候选批处理组合、真实大规模账单性能。文件夹导入等缺失入口无法点击。
- 本轮未修改业务代码。截图和浏览器操作脚本保存在 Git 忽略的 `data/ui-review/`。

## 优先修复的问题

### P1：标签管理只有“建视图”，无法“建标签”

复现：标签管理 → 新建“体验项目” → 出现一个只有“未分类”的视图。该页唯一按钮是“新建（自带未分类）”，不能添加“旅行”“装修”等可选标签，也没有重命名或归档操作。新视图因此无法承担分类工作。

定位：`app/static/workspace-next.js:199` 的最终 `renderTags`；后端已有 `app/main.py:816` 等标签维护端点。

建议：每个视图提供新增标签、重命名和归档操作；批量打标签能力也应有选中流水的界面入口。

### P1：导入失败与重复被压成“已导入 0 个文件”

复现一：上传错误模板 → 预览显示错误，但仍出现“确认导入” → 点击后只显示“已导入 0 个文件”。

复现二：重复上传已导入的微信 CSV → 预览仍显示“1 条” → 确认只显示“已导入 0 个文件”，不说明重复。

复现三：密码 ZIP 成功预览 → 密码自动清空 → 直接确认 → 同样只显示“已导入 0 个文件”。重新预览并再次输入密码后才成功。

定位：`app/static/workspace-next.js:25`、`:26`。确认响应仅统计 `status === imported` 的文件数，未呈现各文件的错误或跳过原因。

建议：逐文件显示成功、失败、重复及原因；全部失败时禁用确认；需要再次输入密码时给出明确的确认步骤。成功结果展示导入流水数、候选数以及进入复核的入口。

### P1：“预览账单”不足以核对实际账单

实际只看到 `ui-alipay.csv：64 条`，看不到交易时间、交易方、金额、收支方向或解析结果。用户无法在确认前判断选错平台、金额正负或字段识别问题。README 声称支持选择文件夹，实际文件控件 `webkitdirectory=false`，也没有另一个文件夹入口。

定位：`app/static/workspace-next.js:25`、`:173`。

建议：逐文件提供明细抽样、收支汇总、异常说明和选择确认；补文件夹入口。

### P1：“已确认转移”筛选查不到刚处理的转移

复现：确认个人转移 → 列表状态为 `personal_transfer_grouped` → 状态选择“已确认转移” → 显示 0 条。回到“全部”可再次看见。批量他人转移使用 `third_party_transfer_grouped`，同样不对应旧筛选值。

定位：`app/static/workspace-next.js:29` 发出 `transfer_grouped`；`app/main.py:1328` 精确比较状态；`:1385` 写入细分状态。

建议：前后端统一状态选项，已确认转移包含个人和他人两类；界面展示中文状态。

### P1：数据库页重复绑定翻页事件

复现：反复进入数据库观察并返回汇总，再进数据库页 → 点击一次“下一页”。网络记录为连续请求 `page=2`、`page=3`、`page=4`、`page=5`，界面最终曾落在第 4 页。可见页码取决于响应先后，不只是多发送了一次请求。

定位：`app/static/workspace-next.js:157`，每次 `renderDatabase` 都在保留的页面节点上注册新的匿名点击处理器。

建议：事件只绑定一次；防止过期请求覆盖当前页。补覆盖“退出页面再回来”的真实浏览器回归。

### P1：用户难以找回已排除的原始流水

复现：搜索“重复咖啡”看到 2 条 → 在候选中保留 A → 回数据页搜索只剩 1 条。原始记录仍在数据库和候选详情中，没有被删除，但数据页没有“含已排除”或“仅已排除”入口。

同时，汇总的“已导入流水”从 64 变为 63；确认转移也会使这个数字减少。后台目前有意共用有效流水口径，因此应优先修正名称与展示入口，不能简单把所有汇总改为包含已排除记录。

定位：`app/main.py:688`、`:766`、`:1607`；`app/static/workspace-next.js:18`、`:190`。

建议：区分“累计导入数”“参与汇总数”和“已排除数”；提供原始流水/有效流水切换及排除原因。

## 可用性问题与建议

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| 导入、完整筛选表单长期占据数据页上方 | 手机用户先滚过很长表单才能看到流水 | 默认突出流水，导入独立打开，筛选折叠且显示已应用条件。 |
| 返回数据页筛选条件丢失 | 复核一条记录后难以回到原来的数据集合 | 保存筛选、排序和页码；“清空”才重置。 |
| 大量操作都是同样深蓝按钮 | “关闭”、查看、保留 A/B 等视觉重要性相同 | 建立主次按钮层级；候选先呈现差异，再呈现决定。 |
| 候选按钮包含整段后果文字 | 表格拥挤、难扫读 | 按钮简明，后果放相邻说明，保持原始证据默认展开的已确认需求。 |
| `pending`、`deferred`、`alipay`、JSON 系统名及英文校验错误外露 | 普通用户需要理解内部术语 | 中文状态、来源和错误；系统名移到高级详情。 |
| 手机导航全部只剩抽象符号 | 需要猜测入口，数据库符号还换行 | 采用可读短名称或可展开菜单。390px 实测页面宽度 398px。 |
| 金额范围、收支方向只存在 API 能力，UI 未提供 | 找特定账目需要逐条看 | 在高级筛选中提供金额、收入/支出/转移。 |
| “稍后”候选只剩详情和撤销 | 继续处理必须先撤销，语义绕 | 明确“继续处理”入口，保留审计要求。 |
| 空汇总只有“暂无流水” | 首次进入缺少下一步指引 | 提供导入账单主操作与支持格式提示。 |

## 需求文档应一并澄清

README 虽然指定了“当前 MVP”优先，但仍存在当前段落间的冲突：

1. “最短导入与验收”“打标策略”描述四种流水打标按钮，实际页面只有“选择标签”。需要明确这四种策略是否仍要求在工作台暴露，还是改为 API 能力。
2. JSON 状态章节说旧关联表不再写入，后面的数据关系章节仍把它们描述成当前关系。
3. 旧“已包含”章节提到账单手工新增和资产快照，而当前脚本重建为五页工作台。这部分已有替代声明，不应直接认定为当前 MVP 漏做。
4. 余额校准、账单计划、LLM 配置页等明确在当前范围之外，本次不作为必须补齐的 UI 缺陷。

## 建议验收顺序

先修复导入错误反馈、标签维护、候选筛选和数据库翻页，再统一流水/汇总统计口径与可追溯入口；随后调整数据页和手机布局。最后按“导入 → 核对流水 → 打标签 → 处理候选 → 返回汇总 → 找回原始证据”完整操作验收。

证据文件：`data/ui-review/results.json`、`extra-results.json` 以及同目录截图。`review.py` 需要新的体验数据库以重放初次导入；不应直接对真实用户数据运行。
